# Сервіс збору `app-ads.txt`

Коротке архітектурне рішення. Ідентифікатори вже є в екосистемі (десятки мільйонів). Завдання сервісу — не відкрити каталог стору, а тримати в актуальному стані видавця, його сайт і файл `https://[домен]/app-ads.txt`. Поки немає HTTP API, верифікатор читає актуальний `body` через `apps.bundle_id → domain_id`.

## Хід думок

Два цикли з ТЗ — різна робота, різний bottleneck.


| Цикл   | По чому йдемо   | Що змінюється                  | Обмеження                                                            |
| ------ | --------------- | ------------------------------ | -------------------------------------------------------------------- |
| Weekly | додаток у сторі | власник, ім’я, сайт, видалення | Apple Lookup ~20 req/min з IP; Play HTML — антибот, не повний weekly |
| Daily  | домен видавця   | тіло `app-ads.txt`             | простий GET; обсяг = унікальні хости, не рядки `apps`                |


Тому **файл не живе на рядку додатка**. Інакше один і той самий текст дублюється на всі ігри студії, а daily читає TOAST мільйони разів. Нормальна модель: додаток → видавець і домен; поточний файл і його хеш — на домені.

Ключ у `apps.bundle_id` — те, чим стор адресує картку: Android package name; iOS — **числовий Apple ID** (`trackId`). Lookup батчиться лише як `id=1,2,…,50`. Запит `bundleId=com.foo` — один id на запит; на десятках мільйонів це в 50 разів менше пропускної. Якщо їхня база — рядок `com.company.app`, ingest мапить у `trackId` (окрема колонка не потрібна: у `bundle_id` кладемо те, чим ходимо в стор).

Інтервали (24 год / 7 днів) — **з моменту останнього успіху**, не з будь-якої спроби. Інакше 429 на Play означає «спимо тиждень». Ретраї — окреме поле `available_at` + backoff `min(60 хв, 1 хв × 2^n)`.

Порожній файл — теж успіх перевірки. Сайт зі стору часто support або соцмережа, не IAB-хост. Покриття ніколи не 100%. Домен не видаляємо: файл можуть викласти завтра. HTML-лендинг і капчу як `app-ads.txt` не зберігаємо.

## Архітектура

Postgres — джерело правди (стан і due). Redis — тупий list id, не delayed-черга і не сховище файлів. Планувальник не ходить у HTTP: короткий `SELECT … FOR UPDATE SKIP LOCKED`, `last_queue_pushed = now()`, commit, пуш у Redis. Claim «вже в черзі» — lease в Postgres (`QUEUE_LEASE`), не TTL ключа. Стан: `apps` → `publishers` і `domains`; на домені — `body` + sha256 і за потреби `app_ads_revisions`; weekly-факти — `app_change_events`, не снапшот кожної перевірки.

Три незалежні контури, один образ, різний env. **Не один процес на все:** три планувальники і свої воркери. Падає Play — iOS і daily по доменах ідуть далі.

```
           ┌─ scheduler CONTOUR=ios      → queue:store:ios      → worker:store (Lookup)
apps  ─────┼─ scheduler CONTOUR=android  → queue:store:android  → worker:store (Play HTML)
domains ───┴─ scheduler CONTOUR=appads   → queue:appads         → worker:appads
```

Код планувальника один (цикл claim → Redis → sleep). У рантаймі три контейнери: `CONTOUR` вибирає **який** due-SQL і **яку** чергу. Воркери: `worker:store` (`CONTOUR=ios|android`) і `worker:appads`. Планувальників по одному на контур (дешеві). Воркери масштабуються репліками і `WORKER_CONCURRENCY`. Apple і Play **не** в одному воркері: різні ліміти; капча Play не повинна стопити iOS.

HTTP у v1 без браузера і без solver капчі. iOS — Lookup (слот = батч до 50 числових id). ~20 req/min × 50 ≈ **1.4M id/добу з однієї IP**; 25M iOS ≈ 18 діб на IP — проксі на iOS не «пізніше», а умова першого проходу. Play — сторінка додатка, сайт видавця з `appstore:developer_url`. У v1 це **best-effort**: беремо всі due, покриття обріже антибот, не семплер. Капча / 429 / мережа — backoff. Немає файлу (404 або HTML без рядків DIRECT/RESELLER) — добовий ритм, `body` порожній. Проксі (`PROXY_URL`) окремо на контур; daily по сайтах видавців і стор не змішуємо.

Швидкість: не token-bucket і не стеля глибини Redis. Налив — `SCHEDULER_BATCH_SIZE` за цикл і `SCHEDULER_INTERVAL` між циклами; воркери крутимо окремо. Due вже в SQL. `SKIP LOCKED` дає кілька реплік без очікування на чужому рядку. Daily due — по `domains`; оцінюємо `COUNT` хостів, не Bundle ID.

## Ключові відмови


| Не робимо в v1                    | Чому                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------ |
| CronJob як обов’язкова модель     | Той самий процес локально і в k8s; sleep = швидкість наливу                                |
| Redis ZSET / Lua delay            | Due і backoff уже в Postgres                                                               |
| Playwright, акаунти, solver       | `app-ads.txt` — GET; капча на десятках мільйонів — не стратегія                            |
| Play HTML як повний weekly        | Антибот. Повний прохід — платний каталог, не ферма браузерів                               |
| Парсинг DIRECT/RESELLER у таблицю | Для збору досить сирого `body`; розбір — окремий шар                                       |
| Публічний HTTP API                | Читання — SQL / DbGate (`apps` → `domains.body`); ендпоінт — коли знадобиться верифікатору |
| Скрейп усього каталогу стору      | Ідентифікатори вже є; сервіс лише актуалізує                                               |




## План імплементації

1. **Контракт даних.** Таблиці `apps` / `publishers` / `domains` / ревізії / події. Наповнення: `INSERT` їхньої бази або демо-seed. Для iOS у `bundle_id` — numeric Apple ID. Планувальник завжди читає due з `apps`/`domains`.
2. **Планувальник.** Той самий бінарник, **три процеси** (`CONTOUR=ios` / `android` / `appads`). Кожен крутить свій цикл і свій due-SQL у свою Redis-чергу. Lease на `last_queue_pushed`. Швидкість наливу — batch і sleep, не глибина list. Не один процес, який по черзі обходить три контури.
3. **Стор-воркер.** Спільний пайплайн (черга, upsert, події). Адаптер Apple Lookup і адаптер Play. Ідемпотентний UPDATE за «seen» `last_successfully_fetched`. Play не обіцяємо як 100% weekly.
4. **App-ads воркер.** GET, ETag/304, sha256, ревізія лише коли змінився справжній файл. Fallback listed host → eTLD+1.
5. **Експлуатація.** Один Docker-образ, три пари сервісів. Інтервали і ліміти — env. Проксі на iOS з першого проходу (квота Lookup); на Play — коли впираємось у антибот; daily — окремий пул.
6. **Далі (не v1).** Розбір рядків `.txt`, API для верифікатора, кілька storefront-країн, каталог замість HTML Play.

v1 вважається зібраним, коли weekly оновлює видавця і домен на iOS, daily тримає актуальний `body` (або свідомо порожній), Play не обіцяємо як повний weekly, а 429 не зсуває тижневе вікно.
