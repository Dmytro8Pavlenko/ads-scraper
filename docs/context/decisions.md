# Decisions

Журнал решений. Пишу сюда, когда вариант согласовали. Контекст — `how-app-ads-txt-works.md`, схема — `database-schema.md`.

Формат: **выбрали** / **отклонили** / **почему**.

---

## Стек

- **Выбрали:** Node.js + TypeScript.
- **Отклонили:** Go/Python для v1.
- **Почему:** один язык с DbGate/скриптами, быстрый старт HTTP и воркеров.

## Откуда Bundle ID

- **Выбрали:** один контракт — таблица `apps`. Колонка `bundle_id` — ключ витрины, не обязательно IAB/iOS bundle string: Android package name; iOS — **числовой Apple ID** (`trackId`), чтобы Lookup шёл батчем `id=1,2,…,50`. Два способа **наполнить**, не два рантайма:
  1. свои данные: `INSERT`/копия их базы (десятки миллионов), iOS уже как `trackId`;
  2. демо: `npm run seed` со статичным списком.
- **Отклонили:** отдельный режим воркеров «seed vs prod»; качать топ чартов при старте compose; отдельная колонка `store_app_id` в v1; считать `com.foo` ключом батча Lookup.
- **Почему:** планировщик всегда читает due из `apps`. Разница только в том, кто положил строки. Их экосистема уже владеет идентификаторами — сервис не скрейпит каталог стора целиком. `bundleId=com.foo` — один id на запрос; на десятках миллионов это не тот канал. Адаптер может сходить по строке по одному (остаток), но ingest на масштаб — числа.

## Планировщик: процесс, не CronJob

- **Выбрали:** постоянно запущенный процесс: батч → sleep → снова. `SCHEDULER_BATCH_SIZE` и `SCHEDULER_INTERVAL` (например 60s) из env.
- **Отклонили:** k8s CronJob / crond в compose как обязательная модель; вечный цикл без sleep (выгребает весь due сразу).
- **Почему:** тот же код локально и в проде. Интервал = скорость налива без token bucket. Compose: сервис со `sleep`, не контейнер cron.

## Хранение `app-ads.txt`

- **Выбрали:** Postgres. Текущее тело и `content_hash` на `domains`. Ревизии — только прошлые тела, 1:N, когда хеш сменился.
- **Отклонили:** колонка на `apps`; Redis как хранилище файла; S3 в v1; файлы на диске сервера; `current_revision_id` (ложное 1:1).
- **Почему:** файл один на домен, не на Bundle ID. Файлы крошечные. Хеш в соседней колонке, чтобы daily не читал `body` из TOAST. Если история содержимого не нужна — `app_ads_revisions` можно не делать.

## Хеш

- **Выбрали:** sha256 текущего body на `domains`. Сравниваем с хешем только что скачанного файла.
- **Отклонили:** каждый раз грузить старый `body` и сравнивать строки; хеш без хранения в БД.
- **Почему:** если оба текста уже в памяти, строки не хуже. Выигрыш — не тащить старое тело из Postgres. Ещё лучше HTTP `ETag` / `If-None-Match` → 304, тогда и качать нечего.

## Интервалы (1 день / 7 дней)

- **Выбрали:** env (`APP_ADS_INTERVAL=24h`, `STORE_INTERVAL=7d`). Обычный ритм — `last_successfully_fetched + interval` (не любая попытка).
- **Отклонили:** таблица `settings`; Redis как источник правды; один `next_fetch_at`/`available_at` и на ритм, и на ретраи.
- **Почему:** два числа из ТЗ, UI нет. Смена периода в env сразу видна в SQL due. Ошибка не должна отодвигать следующее окно на неделю — иначе 429 = «спим 7 дней».

## Очередь, ретраи, идемпотентность

- **Выбрали:**
  - Планировщик не скрейпит: короткий `SELECT … FOR UPDATE SKIP LOCKED`, `last_queue_pushed = now()`, commit, пуш id в Redis. Три очереди: домены / App Store / Play.
  - Обычный ритм: `last_successfully_fetched + env`.
  - Ретраи: `available_at` + `retry_count` (не двигают `last_successfully_fetched`).
  - Claim пуша: `last_queue_pushed` + `$queue_lease` в env.
  - Redis — list. Пока есть занятый слот — `LPOP`. Когда все слоты свободны — `BRPOP` (ждёт элемент или timeout 5–30с, не poll раз в секунду). Перед HTTP сверяет период; свежий успех → дроп без ретрая.
  - Запись успеха: строка не сменилась с момента чтения. Смысл — `last_successfully_fetched IS NOT DISTINCT FROM $seen_at`. В коде сравниваем `date_trunc('milliseconds', …)`: Postgres хранит микросекунды, `Date` в Node — миллисекунды, иначе после первого успеха апдейт никогда не проходит.
  - Те же четыре поля на `apps` и на `domains`.
- **Отклонили:** delayed ZSET и Lua; `available_at` как единый курсор ритма и backoff; держать `FOR UPDATE` на время HTTP; обычный `FOR UPDATE` без `SKIP LOCKED`; точное равенство timestamptz с `Date`; `BRPOP` на каждом слоту.
- **Почему:** delay и due уже в Postgres. Lua не писать. Ошибка ≠ «спим неделю». Дубль пуша закрывает claim, не уникальность list. HTTP не держит слот БД. BRPOP на каждом слоту при пустой очереди размножил бы ожидание.

## Три контура и масштаб

Планировщик = процесс, который берёт due и пушит в Redis. Обработчик = ест очередь и ходит в HTTP.

- **Выбрали:** три пары (один код стора, разные аргументы/env):
  1. домены → `app-ads.txt`
  2. App Store (`store = ios`)
  3. Google Play (`store = android`)
  По умолчанию планировщиков по **1** на контур, обработчиков — **несколько**. Все роли горизонтально масштабируются (`SKIP LOCKED`).
  Env у каждого процесса свой: в коде одни имена (`WORKER_CONCURRENCY`, `PROXY_URL`, `SCHEDULER_BATCH_SIZE`, имя очереди, `store=ios|android`), в деплое три набора значений. Не три префикса в одном процессе.
- **Скорость обработки** крутим числом реплик обработчиков и `WORKER_CONCURRENCY`. Env — желаемое число **id** в полёте, не «слотов HTTP».
  - iOS: слот = один Lookup-батч. `WORKER_CONCURRENCY` округляется **вверх** до кратного `LOOKUP_BATCH_SIZE` (10 → 50, 210 → 250). Неполный последний батч ок, если в очереди меньше 50.
  - Play и app-ads: слот = 1 id, без округления.
- **Отклонили:** один weekly-воркер на оба стора; скорость в первую очередь через enqueue-rate в Redis; для Apple слот = 1 id.
- **Почему:** у Apple и Play разные лимиты, прокси, батч Lookup vs одна страница, капча. Упавший Play не должен стопить iOS. Планировщик дешёвый — размножать его «чтобы быстрее качать» бессмысленно. Lookup умеет `id=1,2,…,50`: 4 запроса по 1 id хуже, чем 1 на 50.

Батч планировщика — `SCHEDULER_BATCH_SIZE`. Потолок глубины Redis (`QUEUE_MAX`) **не фиксируем**: налив уже ограничен batch × interval. Lease (`QUEUE_LEASE`) закрывает «уже в очереди», не глубину list.

## Гонка «первый проход, все `domain_id` NULL»

- **Выбрали:** `UNIQUE(host)` + upsert `ON CONFLICT … RETURNING id`, лучше `SET updated_at = now()`. То же для `publishers (store, store_developer_id)`.
- **Отклонили:** SERIALIZABLE «для миграций»; апдейт `host` в конфликте как смена сущности.
- **Почему:** гонка рантайма, не миграций. Хост у строки `domains` не переименовываем: смена сайта у приложения = новая строка домена + новый `apps.domain_id`. Старый хост может остаться у других игр.

## Стор: браузер, аккаунты, капча, прокси

- **Выбрали v1:** без аккаунтов, без Playwright. iOS — только Lookup API (`sellerUrl`, `artistId`, `trackName`); ~20 req/min × 50 id ≈ 1.4M id/сутки с одной IP — прокси на iOS с первого прохода, не «потом». Play — HTTP страницы `details?id=` и парсер, **best-effort** (все due, покрытие режет антибот), не полный weekly. Капча = ошибка канала + backoff, не solver. Прокси по контуру (квота Apple, антибот Play). Отдельные клиенты/лимиты: Apple / Play / сайты издателей.
- **Отклонили v1:** HTML карточки App Store как запас к Lookup; разгадывание капчи; ферма браузеров; обязательный residential; 42matters как зависимость; обещать Play HTML как weekly на десятках миллионов.
- **Почему:** `app-ads.txt` — простой GET. У Apple нет API «для рекламных сетей под app-ads.txt»; Lookup — ближайший публичный канал, сайт издателя уже в JSON. Play — без публичного API, антибот злее. Капча на масштабе не стратегия. Полный android weekly — платный каталог, не solver.

Daily по сайтам издателей в стор-прокси не смешивать.

## Play: откуда сайт издателя

- **Выбрали:** `<meta name="appstore:developer_url">`, запас — старый JSON `"developerWebsite"` и контактный блок в `AF_initData`.
- **Отклонили:** считать `"developerWebsite"` единственным полем (в текущем HTML его нет).
- **Почему:** без этого title и publisher пишутся, а `developer_url` / `domain_id` остаются NULL, daily по домену не стартует.

## Нет файла `app-ads.txt`

- **Выбрали:** пустой `body` — валидный исход проверки, не дыра. Домен не удаляем, daily ритм тот же. HTML-лендинг / пустой 200 / JSON без строк `DIRECT`/`RESELLER` (и без `OWNERDOMAIN=`) = не файл: тело не пишем (или стираем мусор), `last_error = not app-ads.txt`. Настоящий txt HTML-ом не затираем. Капча / recaptcha / `/sorry/` = ретрай, как 429. Отдельный `status` на `domains` не заводим: хватает `body` + `last_http_status` + `last_error`.
- **Отклонили:** хранить HTML как файл; подставлять `ads.txt` вместо `app-ads.txt`; угадывать другой хост; пожизненно помечать домен мёртвым; колонку `present|missing|blocked`.
- **Почему:** сайт из стора часто support/соцсеть, не IAB-хост. Покрытие никогда не 100%. Файл могут выложить завтра — строка должна остаться в due. ТЗ фиксирует URL `https://[домен]/app-ads.txt`.

## Прокси в env (v1)

- **Выбрали:** опциональный URL (или список URL). Авторизация — внутри URL: `http://user:pass@host:port`. Нет прокси — воркеры идут напрямую.
- **Отклонили:** отдельные `PROXY_USER` / `PROXY_PASS` как обязательные поля; один URL, если нужен round-robin по своим IP.
- **Почему:** так умеют стандартные HTTP-клиенты (`HTTP_PROXY`). У residential-шлюзов сессия/страна часто тоже в username. Отдельные user/pass имеют смысл только если пароль ломает URL (`@`, `:`) или секреты инжектятся порознь — тогда как запас, не как схема v1. Пул = несколько URL через запятую/перевод строки, каждый самодостаточный. Один URL у провайдера тоже ок: round-robin делает их гейт, не мы.

## Ошибки скрейпа vs статус витрины

- **Выбрали:** на `apps` те же `last_http_status` + `last_error`, что на `domains`. `apps.status` только про карточку в сторе (`active` / `removed` / `not_found`).
- **Отклонили:** писать 429/капчу в `status`; отдельную таблицу ошибок.
- **Почему:** иначе не отличить «приложения нет» от «Play показал капчу». `retry_count` / `available_at` — когда ещё раз, не что случилось.

## Журналы

- **Выбрали:** `app_change_events` — только факты weekly (владелец, имя, URL, удаление). Не снапшот каждой проверки и не HTML витрины.
- **Отклонили:** лог каждого daily-HTTP; таблица разобранных DIRECT/RESELLER в v1.
- **Почему:** 50 млн «всё как было» в неделю бессмысленны. Текущее состояние — в `apps` / `publishers` / `domains.body`. Парсинг строк `.txt` можно навесить позже.

## Точки входа

- **Выбрали:** три процесса, три скрипта: `npm run scheduler`, `npm run worker:store`, `npm run worker:appads`. Один Docker-образ, разный `command`. `CONTOUR` у планировщика (`ios|android|appads`) и у стор-воркера (`ios|android`). App-ads воркер без `CONTOUR`. В `src/` в корне — точки входа, общее — в `lib/`, не свалка `utils/`.
- **Отклонили:** `ROLE=scheduler|worker` в одном `main.ts`; три копии планировщика; app-ads внутри `StoreAdapter`.
- **Почему:** планировщик и HTTP-воркер — разная работа. Apple/Play делят пайплайн очереди/upsert/events, HTTP — адаптер. Доменный GET — другая таблица. Код планировщика один цикл и три именованных due-SQL; в рантайме три контейнера.

## Дефолты v1 (чтобы начать код)

- **Миграции / ORM:** Drizzle (`drizzle-orm` + `drizzle-kit`). SQL рядом со схемой, Studio по желанию.
- **`app_ads_revisions`:** писать при смене хеша, только если старое тело само было файлом (HTML в историю не кладём).
- **Парсинг DIRECT/RESELLER:** не в v1, храним сырой `body`. Классификатор «это файл или HTML» — да, разбор счетов — нет.
- **HTTP API наружу:** не в v1. Чтение — SQL / DbGate: `apps.bundle_id` → `domains.body`. Эндпоинт «файл по Bundle ID» — когда понадобится верификатору.
- **Тесты:** vitest по сохранённым сниппетам (Lookup JSON, `example-app-ads.txt`, HTML/капча Play и app-ads). Живой стор в CI не бьём.
- **Backoff:** `min(60 мин, 1 мин × 2^retry_count)`, счётчик растёт; потолка «убить джобу» нет. 404 / «не файл» `app-ads.txt` = успех проверки. 0 результатов Lookup = `status=not_found`, тоже успех (не ретрай). 429/капча/сеть = ретрай.
- **`QUEUE_LEASE`:** 10 минут.
- **Lookup:** слот берёт до `LOOKUP_BATCH_SIZE` id (дефолт 50) и один запрос `id=…`. Play и домены — по одному URL; параллель — число слотов из `WORKER_CONCURRENCY` (см. «Три контура»).
- **Витрина Apple:** `STORE_COUNTRY=us` (один storefront). Несколько стран — позже.
- **Нормализация URL:** как IAB: хост lowercase, без порта/пути; `www` срезаем. Fallback: listed host, затем eTLD+1 (`psl`) — и на 404, и когда ответ не файл.
- **Прочее:** без `QUEUE_MAX`; User-Agent свой, не молчаливый; таймаут HTTP 20 с.
